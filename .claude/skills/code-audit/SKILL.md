# Code Audit

Systematically review code, measure quality **deltas across passes**, and maintain a prioritized backlog of improvements.

## When to use

- Auditing a module, app, or repository.
- Measuring the impact of refactoring across passes.
- Maintaining a backlog of improvements with importance levels.
- Preparing a refactoring or hardening plan.
- Reviewing code before/after a significant change (see `refactoring`, `solid-principles`, `design-patterns`).

## Files (in the project)

| File | Purpose |
|------|---------|
| `docs/audit/auditory.md` | Audit history — one entry per pass, with measured deltas |
| `docs/audit/track_auditory.md` | Improvement backlog — suggestions with importance and status |
| `docs/audit/reports/YYYY-MM-DD-pass-N.md` | Raw snapshot generated by `audit.sh` for that pass |

Keep the three in sync: every delta in `auditory.md` should be explained by changes recorded in `track_auditory.md` (or explicitly dismissed). The raw snapshot is the evidence; the history is the narrative; the backlog is the plan.

## Framework-specific audits

The metrics and the delta format are language-agnostic. For a framework pack:

- **Frappe**: also check DocType descriptions, permissions, `hooks.py`, patches, raw SQL, `ignore_permissions`, unbounded queries, scheduler jobs, and the `bench` runbook. Load the `frappe-*` skills and use the Frappe signals from `audit.sh`.
- **Other languages**: the script detects Python, Node, Go, Rust, Java, .NET, Ruby, and PHP; add framework checks only when the pack exists.

## Default language

**English**, unless the user asks otherwise.

## Agent identification (multi-agent)

The same rules apply to opencode and Claude Code. Stamp each pass:

| Tool | ID |
|------|----|
| opencode | `OC` |
| Claude Code | `AC` |

Precedence: (1) runtime identity; (2) env vars — `OPENCODE` set → `OC`, `CLAUDE_PROJECT_DIR`/`CLAUDE_CODE_ENTRYPOINT` set → `AC`; (3) on conflict, trust runtime identity.

## Measured metrics (deltas per pass)

For every pass, record the metrics before (previous) and after (current), and the **delta**:

| Metric | Meaning | Source |
|--------|---------|--------|
| Source files | Files in scope | `audit.sh` |
| Source lines | Total LOC | `audit.sh` |
| Non-blank lines | Physical code volume | `audit.sh` |
| TODO/FIXME/HACK | Known debt markers | `audit.sh` |
| Largest files | Size outliers | `audit.sh` |
| Git churn (90d) | Change frequency | `audit.sh` |
| Cyclomatic complexity | Avg/max complexity | `--checks` (radon/gocyclo/etc.) |
| Code smells | Count of smells found | Manual (see `refactoring`) |
| Duplication | Percentage duplicated | `jscpd`/PMD or manual |
| Test coverage | Percentage covered | Test runner/coverage tool |
| Open improvements | Backlog size | `track_auditory.md` |

Use the subset that applies; keep it **identical across passes** so deltas are comparable. If a metric was not measured, write `n/a` — do not invent a number.

## Importance scale

Used in `track_auditory.md`. Highest first:

| Level | Meaning |
|-------|---------|
| **Critical** | Bug risk, security, data loss, or access control — fix now |
| **High** | Significant maintainability/performance issue — fix soon |
| **Medium** | Worth doing, non-urgent |
| **Low** | Cosmetic or nice-to-have |

## Procedure

### 0) Define scope and prepare

State the path/module being audited and fix the metric set once. Ensure:

```
docs/audit/
├── auditory.md
├── track_auditory.md
└── reports/
```

### 1) First pass — baseline

- Run the snapshot:

```bash
./.claude/scripts/audit.sh --scope <scope> \
  --out "docs/audit/reports/$(date -u +%Y-%m-%d)-pass-1.md"
```

- Read the snapshot and inspect the highest-risk files.
- Append **Pass 1** to `docs/audit/auditory.md` (no delta yet).
- Add the first improvement suggestions to `docs/audit/track_auditory.md`.

### 2) Subsequent passes — deltas

- Compute the next pass number from `auditory.md` (`## Pass N` headings).
- Save a new snapshot with `--out docs/audit/reports/YYYY-MM-DD-pass-N.md`.
- Append a pass entry with **Previous → Current → Delta** using the same metric set.
- Move resolved suggestions from **Open** to **Resolved**.
- Add new suggestions for findings that are still open.

### 3) Record findings

For each issue, add a suggestion row under **Open** in `track_auditory.md`:

- **ID**: `A-NN`, sequential.
- **Improvement**: a specific action, not a vague concern.
- **Importance**: Critical/High/Medium/Low.
- **Area**: file/module.
- **Detected**: pass number.
- **Technique**: the refactoring/design/test action that fixes it (e.g., Extract Class, Add regression test, ADR).

### 4) Keep files in sync

- Every improvement maps to an observed change in `auditory.md`.
- If a pass changed nothing, say so explicitly.
- If a suggestion is rejected, record the reason (do not silently delete it).

## Improvement suggestions

Every audit produces **actionable suggestions**, not just metrics.

### Minimum per pass

- All **Critical** and **High** findings.
- At least **3–5** suggestions total, even on a healthy codebase (often medium/low).
- If nothing is worth fixing, say so explicitly and record why.

### What makes a good suggestion

A good suggestion is:

- **Specific**: names the file/module and the action.
- **Actionable**: a developer can start without re-reading the whole audit.
- **Justified**: links to the smell/risk and the technique.
- **Sized**: one small refactor or test, not "rewrite the module".
- **Traceable**: has an ID and a pass.

### Mapping findings to techniques

| Finding | Suggested action | Skill |
|---------|------------------|-------|
| Long method / high complexity | Extract Method, Guard Clauses | `refactoring` |
| God class / divergent change | Extract Class, Move Method | `refactoring` |
| Repeated type switch | Replace Conditional with Polymorphism | `refactoring`, `design-patterns` |
| Duplicate logic | Extract Method / Pull Up Method | `refactoring` |
| Long parameter list / data clump | Introduce Parameter Object | `refactoring` |
| Feature envy / message chains | Move Method / Hide Delegate | `refactoring` |
| Coupling to infrastructure | Ports and adapters, DI | `solid-principles`, `design-patterns` |
| Missing regression test | Add a failing test first | `test-driven-development` |
| Flaky/slow tests | Fix the test or move to integration | `testing-patterns` |
| Missing README/ADR/runbook | Write the smallest doc | `documentation` |
| Architecture violation | Add an architecture test | `testing-patterns` (`architecture-tests.md`) |
| Weak assertions / mutants survive | Strengthen tests, mutation testing | `testing-patterns` (`mutation-testing.md`) |

### Suggestion format

```markdown
| ID | Improvement | Importance | Area | Detected | Technique |
|----|-------------|------------|------|----------|-----------|
| A-01 | Extract pricing rules from `OrderService` | High | `src/orders/service.py` | Pass 2 | Extract Class |
| A-02 | Add a regression test for duplicate invoice numbers | Critical | `src/invoices.py` | Pass 2 | TDD red test |
```

### `docs/audit/reports/YYYY-MM-DD-pass-N.md`

Raw output of `audit.sh` for that pass. It is evidence, not a curated document. Do not edit it after the fact; add a new pass instead.

## Guardrails

- **Fix one metric set and stick to it** — changing metrics between passes makes deltas meaningless.
- **Baseline first** — pass 1 establishes the reference; deltas start at pass 2.
- **Tag importance honestly** — reserve `Critical` for real bug/security risk.
- **Every pass produces suggestions** — at least the Critical/High findings, plus 3–5 total.
- **Make suggestions actionable** — specific file, action, technique, one step.
- **Do not invent metrics** — write `n/a` when not measured.
- **Attribute every pass to an agent** (`OC`/`AC`).
- **Keep the snapshot raw** — do not rewrite history; add a new pass.
- **Write in English** by default.

## Common mistakes

| Mistake | Why It Fails | Fix |
|---------|--------------|-----|
| Changing metrics between passes | Deltas are not comparable | Fix the metric set in pass 1 |
| No baseline | Can't measure improvement | Always record pass 1 as reference |
| Metrics without suggestions | Audit produces no action | Add suggestions for every finding |
| Vague suggestions | Backlog is unusable | Name file, action, technique, size |
| Missing importance | Can't prioritize | Tag every item Critical/High/Medium/Low |
| Forgetting to move items to Resolved | Backlog looks stale | Update status every pass |
| Editing an old snapshot | History is lost | Add a new pass |
| Over-measuring trivial metrics | Noise, not signal | Measure what matters for the project |
